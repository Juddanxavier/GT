# Plan 02-03: CASL Permissions Package

## Objective

Create a shared `@repo/permissions` package with CASL ability definitions for all four roles (superadmin, tenant-admin, staff, customer). This package enforces authorization rules for shipment bill amounts, quote management, tenant/branch administration, and data scoping.

**Purpose:** CASL permissions are the authorization backbone used by both Hono API middleware and React UI components. Defining them in a shared package ensures a single source of truth for access control.

**Output:** Type-safe CASL ability definitions exported from `@repo/permissions`.

    5. **Create `packages/permissions/src/abilities.ts` — CASL ability builder:**

       ```typescript
       /** @format */
       
       import { AbilityBuilder, Ability, type AbilityClass } from '@casl/ability';
       import type { Action, Subject, PermissionContext, ResourceContext } from './types';
       
       type AppAbility = Ability<[Action, Subject]>;
       const AppAbility = Ability as AbilityClass<AppAbility>;
       
       /**
        * Define CASL abilities based on the user's role and context.
        * 
        * Rules are evaluated in order. The last matching rule wins.
        * Use `cannot` AFTER `can` to create exceptions (e.g., staff can manage
        * shipments but cannot update billAmount).
        * 
        * @param user - The user's permission context (role, tenantId, branchId)
        * @returns A CASL Ability instance with all applicable rules
        */
       export function defineAbilityFor(user: PermissionContext) {
         const { can, cannot, build } = new AbilityBuilder(AppAbility);
         
         const isSuperadmin = user.role === 'superadmin';
         const isTenantAdmin = user.role === 'tenant-admin';
         const isStaff = user.role === 'staff';
         const isCustomer = user.role === 'customer';
         
         // Effective tenant ID (superadmin can override via X-Tenant-ID)
         const effectiveTenantId = user.overrideTenantId ?? user.tenantId;
         
         // ── SUPERADMIN: Cross-tenant access, full control ──
         if (isSuperadmin) {
           can('manage', 'all'); // Superadmin can do everything
         }
         
         // ── TENANT-ADMIN: Own org management ──
         if (isTenantAdmin) {
           // Full CRUD on branches, customers, users within own tenant
           can('manage', 'branch');
           can('manage', 'customer');
           can('manage', 'user');
           can('manage', 'shipment');
           can('manage', 'shipment:billAmount'); // Can edit bill amounts
           can('manage', 'quote');
           can('manage', 'invoice');
           cannot('manage', 'tenant'); // Cannot create/delete orgs, only superadmin can
         }
         
         // ── STAFF: Branch-level operations ──
         if (isStaff) {
           can('manage', 'customer');
           can('manage', 'user');
           can('create', 'shipment'); // Can create shipments
           can('read', 'shipment'); // Can view shipments
           can('update', 'shipment'); // Can update non-bill fields
           can('read', 'shipment:billAmount'); // Can SEE bill amounts
           cannot('update', 'shipment:billAmount'); // CANNOT edit bill amounts
           can('update', 'quote'); // Can respond to quotes with price
           can('read', 'quote');
           can('read', 'invoice');
         }
         
         // ── CUSTOMER: Own data only ──
         if (isCustomer) {
           can('create', 'quote'); // Can initiate a quote request
           can('read', 'quote'); // Can see their own quotes
           can('read', 'shipment'); // Can see their own shipments
           can('read', 'invoice'); // Can see their own invoices
           can('update', 'user'); // Can update own profile
           // Cannot: create/update shipments, manage branches, see other customers
         }
         
         // ── DATA SCOPING: Filter by tenant/branch/owner ──
         // These are enforced at the middleware/query level, not in CASL abilities.
         // CASL handles WHAT actions, middleware handles WHICH records.
         // See guards.ts for data-scoping helpers.
         
         return build();
       }
       
       /**
        * Check if a user can perform an action on a subject.
        * Convenience wrapper around ability.can().
        */
       export function can(user: PermissionContext, action: Action, subject: Subject): boolean {
         const ability = defineAbilityFor(user);
         return ability.can(action, subject);
       }
       ```

    1. **Create `packages/permissions/src/guards.ts`** — Data-scoping helpers:

       ```typescript
       /** @format */
       
       import { can, defineAbilityFor } from './abilities';
       import type { Action, Subject, PermissionContext, ResourceContext } from './types';
       
       /**
        * Check if a user has permission AND the resource belongs to their scope.
        * This is the primary guard function used by API route handlers.
        * 
        * Example:
        *   const shipment = await getShipment(id);
        *   if (!canAccess(user, 'update', 'shipment', shipment)) {
        *     return c.json({ error: 'Forbidden' }, 403);
        *   }
        */
       export function canAccess(
         user: PermissionContext,
         action: Action,
         subject: Subject,
         resource?: ResourceContext,
       ): boolean {
         const ability = defineAbilityFor(user);
         
         // First check: does the user have this ability at all?
         if (!ability.can(action, subject)) {
           return false;
         }
         
         // Second check: data scoping
         // If no resource context provided, skip data scoping (only check ability)
         if (!resource) {
           return true;
         }
         
         // Determine the effective tenant ID (superadmin can override)
         const effectiveTenantId = user.overrideTenantId ?? user.tenantId;
         
         // If user has a tenant scope and resource has a tenantId, they must match
         // (unless user is superadmin without overrideTenantId — superadmin sees all)
         if (effectiveTenantId && resource.tenantId && effectiveTenantId !== resource.tenantId) {
           // Superadmin without override can see all tenants
           if (user.role !== 'superadmin' || user.overrideTenantId) {
             return false;
           }
         }
         
         // Staff are scoped to their branch (can also see org-wide data)
         if (user.role === 'staff' && user.branchId && resource.branchId) {
           // Staff can see their own branch's data
           if (resource.branchId !== user.branchId) {
             // But also allow if it's within their org (no branch filter = org-wide)
             // If branchId filter specifically doesn't match, deny
             return false;
           }
         }
         
         // Customer data scoping: only their own data
         if (user.role === 'customer' && resource.ownerId) {
           if (resource.ownerId !== user.userId) {
             return false;
           }
         }
         
         return true;
       }
       
       /**
        * Build a tenant-scoped WHERE condition for Drizzle queries.
        * Returns the tenantId and optional branchId that should be used
        * as query filters.
        */
       export function queryScope(user: PermissionContext): {
         tenantId?: string;
         branchId?: string;
         ownerId?: string;
       } {
         const effectiveTenantId = user.overrideTenantId ?? user.tenantId;
         
         switch (user.role) {
           case 'superadmin':
             // Superadmin with override sees that tenant
             if (user.overrideTenantId) {
               return { tenantId: user.overrideTenantId };
             }
             // Superadmin without override sees all
             return {};
           case 'tenant-admin':
           case 'staff':
             return {
               tenantId: effectiveTenantId ?? undefined,
               branchId: user.branchId ?? undefined,
             };
           case 'customer':
             return { ownerId: user.userId };
           default:
             return {};
         }
       }
       
       /**
        * Role-based access helper for route-level protection.
        * Used in middleware to check if user has the required role.
        */
       export function hasRole(user: PermissionContext, ...roles: string[]): boolean {
         return roles.includes(user.role);
       }
       ```

## Threat Model

### Trust Boundaries
| Boundary | Description |
|----------|-------------|
| `API middleware → CASL ability` | Permission decision is trusted; must not be bypassable |
| `CASL ability → DB query scope` | Data-scoping filters are applied; must match ability rules |

### STRIDE Threat Register
| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-11 | Elevation of Privilege | `defineAbilityFor` | mitigate | Role is read from session (set by Better Auth, not user-controlled). Ability rules are read-only, compiled at request time. |
| T-02-12 | Tampering | `canAccess` | mitigate | Data-scoping checks use server-side session data (userId, tenantId). Client cannot modify these values. |
| T-02-13 | Information Disclosure | `queryScope` | mitigate | `queryScope` returns filters that limit DB queries. Even if a user requests data outside their scope, the WHERE clause restricts results. Defense-in-depth with RLS (Plan 02-07). |
| T-02-14 | Elevation of Privilege | `hasRole` bypass | accept | `hasRole` is a convenience helper. Route-level middleware uses it, but the primary enforcement is CASL abilities via `canAccess`. RLS adds defense-in-depth. |
