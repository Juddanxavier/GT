# Plan 02-06: Route Guards — CASL Authorization Middleware & Admin Access Control

## Objective

Integrate the CASL permissions package into Hono middleware for API route protection, and create admin app layout-level access control that restricts admin access to staff roles only (superadmin, tenant-admin, staff).

**Purpose:** Route guards are the enforcement layer for all authorization rules. Without them, permissions are just definitions. This plan wires CASL into the request pipeline so every API call is checked.

**Output:** Hono authorization middleware that checks CASL abilities before route execution, and admin layout that redirects customers.

    Create `apps/api/src/middleware/authorization.ts` with CASL-powered route guard middleware:

    ```typescript
    /** @format */
    
    import type { Context, Next } from 'hono';
    import { createFactory } from 'hono/factory';
    import {
      canAccess,
      hasRole,
      queryScope,
      type Action,
      type Subject,
      type PermissionContext,
      type ResourceContext,
    } from '@repo/permissions';
    
    // Possible action: Subject pairs used in route definitions
    export type GuardAction = Action;
    export type GuardSubject = Subject;
    
    /**
     * Create a middleware that requires the user to have a specific role.
     * Use on admin routes to ensure only staff roles can access.
     * 
     * Example:
     *   app.get('/admin/shipments', requireRole('superadmin', 'tenant-admin', 'staff'), handler)
     */
    export function requireRole(...roles: string[]) {
      return async function roleGuard(c: Context, next: Next) {
        const user = c.get('user');
        
        if (!user) {
          return c.json({ error: 'Authentication required' }, 401);
        }
        
        // Build PermissionContext from session + tenant middleware
        const permissionContext: PermissionContext = {
          userId: user.id,
          role: user.role as PermissionContext['role'],
          tenantId: c.get('tenantId') ?? user.tenantId,
          branchId: user.branchId,
          overrideTenantId: c.get('tenantId'), // Comes from X-Tenant-ID if set
        };
        
        if (!hasRole(permissionContext, ...roles)) {
          // For API routes, return 403
          const accept = c.req.header('Accept') ?? '';
          if (accept.includes('json') || c.req.header('Content-Type')?.includes('json')) {
            return c.json({ error: 'Forbidden: insufficient permissions' }, 403);
          }
          // For browser requests (admin app), redirect to unauthorized
          return c.redirect('/unauthorized');
        }
        
        await next();
      };
    }
    
    /**
     * Create a middleware that checks a specific CASL ability.
     * Use on individual route handlers for fine-grained access control.
     * 
     * Example:
     *   app.post('/api/shipments', requireAbility('create', 'shipment'), handler)
     *   app.patch('/api/shipments/:id/bill', requireAbility('update', 'shipment:billAmount'), handler)
     */
    export function requireAbility(action: Action, subject: Subject) {
      return async function abilityGuard(c: Context, next: Next) {
        const user = c.get('user');
        
        if (!user) {
          return c.json({ error: 'Authentication required' }, 401);
        }
        
        const permissionContext: PermissionContext = {
          userId: user.id,
          role: user.role as PermissionContext['role'],
          tenantId: c.get('tenantId') ?? user.tenantId,
          branchId: user.branchId,
          overrideTenantId: c.get('tenantId'),
        };
        
        if (!canAccess(permissionContext, action, subject)) {
          return c.json({ error: 'Forbidden: insufficient permissions' }, 403);
        }
        
        await next();
      };
    }
    
    /**
     * Middleware factory that checks ability against a specific resource.
     * Use for resource-specific access control (e.g., "can this user update THIS shipment?").
     * 
     * Example:
     *   app.patch('/api/shipments/:id', requireResourceAbility('update', 'shipment', (c) => ({
     *     tenantId: shipment.tenantId,
     *     branchId: shipment.branchId,
     *   })), handler)
     */
    export function requireResourceAbility(
      action: Action,
      subject: Subject,
      resourceFn: (c: Context) => ResourceContext | Promise<ResourceContext>,
    ) {
      return async function resourceAbilityGuard(c: Context, next: Next) {
        const user = c.get('user');
        
        if (!user) {
          return c.json({ error: 'Authentication required' }, 401);
        }
        
        const permissionContext: PermissionContext = {
          userId: user.id,
          role: user.role as PermissionContext['role'],
          tenantId: c.get('tenantId') ?? user.tenantId,
          branchId: user.branchId,
          overrideTenantId: c.get('tenantId'),
        };
        
        const resource = await resourceFn(c);
        
        if (!canAccess(permissionContext, action, subject, resource)) {
          return c.json({ error: 'Forbidden: insufficient permissions' }, 403);
        }
        
        await next();
      };
    }
    
    /**
     * Helper to attach tenant-scoped query filters to Hono context.
     * Downstream route handlers use this to scope their Drizzle queries.
     * 
     * Example:
     *   const { tenantId, branchId } = getQueryScope(c);
     *   const shipments = await db.select().from(shipments)
     *     .where(eq(shipments.tenantId, tenantId));
     */
    export function getQueryScope(c: Context) {
      const user = c.get('user');
      
      if (!user) {
        return {};
      }
      
      const permissionContext: PermissionContext = {
        userId: user.id,
        role: user.role as PermissionContext['role'],
        tenantId: c.get('tenantId') ?? user.tenantId,
        branchId: user.branchId,
        overrideTenantId: c.get('tenantId'),
      };
      
      return queryScope(permissionContext);
    }
    ```

    **Why middleware factory pattern:** `requireRole()` and `requireAbility()` return middleware functions, allowing them to be used as Hono middleware in route definitions. This is cleaner than checking permissions inside route handlers.

    **Why separate requireRole from requireAbility:** `requireRole` is coarser and used for route-group-level access (e.g., all admin routes need a staff role). `requireAbility` is finer and used for individual route actions (e.g., only superadmin/tenant-admin can update billAmount). This separation aligns with CASL's ability→action model.

    **Why requireResourceAbility:** This is the most granular guard — it checks ability AND data scoping for a specific resource. For example, it checks not just "can user update shipments?" but "can user update THIS specific shipment that belongs to another tenant?" The resource function receives the Hono context and returns the resource's ownership data.

       ```typescript
       /** @format */
       
       import { serve } from '@hono/node-server';
       import { Hono } from 'hono';
       import { cors } from 'hono/cors';
       import { auth } from './auth';
       import { sessionMiddleware } from './middleware/auth';
       import { tenantMiddleware, type TenantVariables } from './middleware/tenant';
       import { requireRole, requireAbility } from './middleware/authorization';
       
       // Import types
       import type { AuthVariables } from './middleware/auth';
       
       type AppVariables = AuthVariables & TenantVariables;
       
       const app = new Hono<{ Variables: AppVariables }>();
       
       // ── Middleware ──
       
       app.use(
         '/api/auth/*',
         cors({
           origin: ['http://localhost:3000'],
           allowHeaders: ['Content-Type', 'Authorization'],
           allowMethods: ['POST', 'GET', 'OPTIONS'],
           exposeHeaders: ['Content-Length'],
           maxAge: 600,
           credentials: true,
         }),
       );
       
       app.use('*', cors({
         origin: ['http://localhost:3000'],
         credentials: true,
       }));
       
       // Auth handler
       app.on(['POST', 'GET'], '/api/auth/*', (c) => {
         return auth.handler(c.req.raw);
       });
       
       // Session
       app.use('*', sessionMiddleware);
       
       // Tenant
       app.use('*', tenantMiddleware);
       
       // ── Routes ──
       
       // Health (no auth required)
       app.get('/', (c) => c.json({ message: 'ShipTrack API' }));
       
       // Debug (no auth required)
       app.get('/api/debug/tenant', (c) => {
         return c.json({
           tenantId: c.get('tenantId'),
           tenantSource: c.get('tenantSource'),
           authenticated: !!c.get('user'),
         });
       });
       
       // Protected routes — staff only
       app.get('/api/staff/ping', requireRole('superadmin', 'tenant-admin', 'staff'), (c) => {
         return c.json({ message: 'Staff access granted' });
       });
       
       // Bill amount write protection — superadmin & tenant-admin only
       app.patch('/api/shipments/:id/bill', requireAbility('update', 'shipment:billAmount'), (c) => {
         return c.json({ message: 'Bill amount update allowed' });
       });
       
       // Catch-all for future API routes
       app.get('/api/*', (c) => c.json({ message: 'API route' }));
       
       serve({
         fetch: app.fetch,
         port: Number(process.env.PORT) || 3001,
       });
       ```

    3. **Update `apps/admin/app/layout.tsx`** — Add role-based access control at the layout level:
       ```tsx
       'use client';
       
       import { useRouter } from 'next/navigation';
       import { useEffect, type ReactNode } from 'react';
       import { authClient } from '@/lib/auth-client';
       import './globals.css';
       
       // Roles allowed to access admin app
       const ALLOWED_ROLES = ['superadmin', 'tenant-admin', 'staff'];
       
       export default function RootLayout({ children }: { children: ReactNode }) {
         const router = useRouter();
         const { data: session, isPending } = authClient.useSession();
         
         useEffect(() => {
           if (isPending) return;
           
           if (!session) {
             router.push('/login');
             return;
           }
           
           const userRole = (session.user as Record<string, unknown>).role as string;
           if (!ALLOWED_ROLES.includes(userRole)) {
             router.push('/unauthorized');
           }
         }, [session, isPending, router]);
         
         // Show nothing while checking auth (flash prevention)
         if (isPending) {
           return (
             <html lang="en">
               <body>
                 <div className="flex items-center justify-center min-h-screen">
                   <p className="text-muted-foreground">Loading...</p>
                 </div>
               </body>
             </html>
           );
         }
         
         // Don't render children if no session or unauthorized
         // (redirect will happen in effect)
         if (!session || !ALLOWED_ROLES.includes((session.user as Record<string, unknown>).role as string)) {
           return (
             <html lang="en">
               <body />
             </html>
           );
         }
         
         return (
           <html lang="en">
             <body>{children}</body>
           </html>
         );
       }
       ```

    **Why layout-level auth for admin app:** The root layout wraps ALL pages. Checking auth at the layout level prevents unauthorized access to ANY admin page, even if a user directly navigates to `/shipments` or `/customers`. Route-level checks in the API are the primary security layer; layout-level checks are UX polish (prevent showing empty pages).

    **Why `ALLOWED_ROLES` in layout vs CASL:** The admin app doesn't import `@repo/permissions` yet (it will use `@casl/react` for UI-level permission checks later). For Phase 2, a simple role array check is sufficient to prevent customer access. When the admin app gets `@casl/react` in Phase 4+, this can be replaced with proper CASL ability checks.

## Threat Model

### Trust Boundaries
| Boundary | Description |
|----------|-------------|
| `Admin app → Hono API` | Authenticated requests with session cookies from staff users |
| `Customer browser → Hono API` | Authenticated requests from customer (should be blocked at admin routes) |

### STRIDE Threat Register
| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-23 | Elevation of Privilege | requireRole | mitigate | Role is read from session (set by Better Auth server-side). Client cannot modify their role. |
| T-02-24 | Elevation of Privilege | requireAbility | mitigate | Ability checks use CASL rules compiled from server-side role data. Client cannot inject abilities. |
| T-02-25 | Bypass | Layout-level check | accept | Layout-level role check is UX polish only. API-level requireRole middleware is the primary enforcement. If layout check is bypassed (e.g., JS disabled), the API still blocks unauthorized access. |
| T-02-26 | Information Disclosure | Unauthorized page | accept | Page reveals "admin panel restricted to staff" — minimal information disclosure. No specific data about roles or permissions leaked. |
