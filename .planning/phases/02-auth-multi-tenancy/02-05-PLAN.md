# Plan 02-05: Tenant Resolver Middleware

## Objective

Create a Hono middleware that dynamically resolves the current tenant from the incoming request. For the admin app, the tenant is implicit from the authenticated user (or overridden via X-Tenant-ID header for superadmin). For portals (future Phase 8), the middleware reads the request host header and looks up the domain in the `tenant_domains` table.

**Purpose:** Every downstream handler needs to know which tenant the request is for. Instead of repeating domain→tenant resolution in every route, this middleware does it once and injects the result.

**Output:** Tenant resolver middleware that caches domain→tenant mappings and injects tenantId into Hono context.

    Create `apps/api/src/middleware/tenant.ts` with the tenant resolver middleware:

    ```typescript
    /** @format */
    
    import type { Context, Next } from 'hono';
    import { db } from '../db';
    import { tenantDomains, tenants } from '../db/schema';
    import { eq } from 'drizzle-orm';
    
    /**
     * In-memory cache for domain→tenantId lookups.
     * Simple Map-based cache with TTL.
     * 
     * In Phase 3, this will be replaced with Redis for persistence across
     * restarts and for cache invalidation when domains change.
     */
    const domainCache = new Map<string, { tenantId: string; expiresAt: number }>();
    const CACHE_TTL_MS = 5 * 60 * 1000; // 5 minutes
    
    /**
     * Tenant info injected into Hono context variables.
     */
    export type TenantVariables = {
      /**
       * The resolved tenant ID for this request.
       * - Admin: from authenticated user's tenantId (or X-Tenant-ID override)
       * - Portal: from domain→tenant lookup in tenant_domains table
       * - null: if tenant cannot be determined (pre-auth requests, health checks)
       */
      tenantId: string | null;
      
      /**
       * How the tenant was resolved, for debugging.
       */
      tenantSource: 'user' | 'domain' | 'header' | null;
    };
    
    /**
     * Custom error for tenant resolution failures.
     */
    export class TenantResolutionError extends Error {
      constructor(message: string) {
        super(message);
        this.name = 'TenantResolutionError';
      }
    }
    
    /**
     * Look up a tenant by domain in the database, using cache.
     */
    async function resolveTenantByDomain(host: string): Promise<string | null> {
      // Normalize domain: remove port, lowercase
      const domain = host.split(':')[0]?.toLowerCase() ?? '';
      
      if (!domain || domain === 'localhost') {
        return null;
      }
      
      // Check cache
      const cached = domainCache.get(domain);
      if (cached && cached.expiresAt > Date.now()) {
        return cached.tenantId;
      }
      
      // Look up in database
      try {
        const result = await db
          .select({ tenantId: tenantDomains.tenantId })
          .from(tenantDomains)
          .where(eq(tenantDomains.domain, domain))
          .limit(1);
        
        if (result.length > 0 && result[0]) {
          const tenantId = result[0].tenantId;
          // Cache the result
          domainCache.set(domain, {
            tenantId,
            expiresAt: Date.now() + CACHE_TTL_MS,
          });
          return tenantId;
        }
        
        // Cache negative result too (prevents repeated DB lookups for unknown domains)
        domainCache.set(domain, {
          tenantId: '',
          expiresAt: Date.now() + CACHE_TTL_MS,
        });
        return null;
      } catch (error) {
        console.error('Tenant domain lookup failed:', error);
        return null;
      }
    }
    
    /**
     * Hono middleware that resolves the current tenant from the request.
     * 
     * Resolution strategy (in priority order):
     * 1. X-Tenant-ID header — superadmin override (only honored if user is superadmin)
     * 2. Authenticated user's tenantId — from session
     * 3. Request host — domain→tenant lookup (for portal access)
     * 
     * This middleware must run AFTER sessionMiddleware so user info is available.
     */
    export async function tenantMiddleware(c: Context, next: Next) {
      let tenantId: string | null = null;
      let tenantSource: 'user' | 'domain' | 'header' | null = null;
      
      // Strategy 1: X-Tenant-ID header (superadmin override)
      const headerTenantId = c.req.header('X-Tenant-ID');
      const user = c.get('user') as { role?: string } | null;
      
      if (headerTenantId && user?.role === 'superadmin') {
        tenantId = headerTenantId;
        tenantSource = 'header';
      }
      
      // Strategy 2: Authenticated user's tenantId
      if (!tenantId && user) {
        const userTenantId = (user as Record<string, unknown>).tenantId;
        if (userTenantId && typeof userTenantId === 'string') {
          tenantId = userTenantId;
          tenantSource = 'user';
        }
      }
      
      // Strategy 3: Request host domain lookup
      if (!tenantId) {
        const host = c.req.header('host');
        if (host) {
          tenantId = await resolveTenantByDomain(host);
          if (tenantId) {
            tenantSource = 'domain';
          }
        }
      }
      
      // Inject tenant info into context
      c.set('tenantId', tenantId);
      c.set('tenantSource', tenantSource);
      
      await next();
    }
    
    /**
     * Clear the domain cache (useful for testing or after domain changes).
     */
    export function clearTenantCache(): void {
      domainCache.clear();
    }
    ```

    **Why in-memory cache instead of Redis in Phase 2:** Redis infrastructure comes in Phase 3 (Infrastructure Backbone). For Phase 2, a simple in-memory Map with TTL is sufficient for development. The cache will be replaced with Redis in Phase 3.

    **Why TTL-based cache:** Domain→tenant mappings change rarely (only when new portals are added). A 5-minute TTL prevents stale data without requiring cache invalidation infrastructure.

    **Why cache negative results:** Prevents repeated DB lookups for unknown domains (bots, misconfigured clients). The empty string tenantId signals "looked up but not found."

## Threat Model

### Trust Boundaries
| Boundary | Description |
|----------|-------------|
| `Browser → Hono API` | Host header and X-Tenant-ID header cross network boundary |
| `Middleware → Drizzle` | Domain→tenant lookup queries tenant_domains table |

### STRIDE Threat Register
| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-19 | Spoofing | Host header | mitigate | Host header is user-controlled. Domain lookup is only used for tenant resolution when user is NOT authenticated. Authenticated users always get tenant from their session (not host header). |
| T-02-20 | Tampering | X-Tenant-ID header | mitigate | X-Tenant-ID is only honored for superadmin users. Regular users' tenant comes from their session (immune to header manipulation). Superadmin authentication prevents unauthorized override. |
| T-02-21 | Information Disclosure | Negative cache | accept | Unknown domains are cached as empty string. No sensitive data leaked — only the fact that the domain is not registered. |
| T-02-22 | Denial of Service | In-memory cache | accept | The cache Map could grow unbounded with many unique domains. In practice, the number of tenant domains is small (<100). Phase 3 moves to Redis with bounded memory. |
