# Plan 02-07: RLS Policies & Phase 2 Verification

## Objective

Add PostgreSQL Row-Level Security as a defense-in-depth layer for tenant isolation, and run a comprehensive verification of all Phase 2 functionality. RLS ensures that even if an application-level query misses the tenantId filter, the database itself prevents cross-tenant data access.

**Purpose:** RLS is the last line of defense for tenant isolation. Combined with CASL permissions and query-scoped Drizzle filters, it creates a defense-in-depth model where three independent layers must all fail for data to leak.

**Output:** RLS policies on tenant-scoped tables + verified end-to-end auth flow.

<interfaces>
Tables requiring RLS:
- tenant — organization table (RLS: tenant can see own row; superadmin sees all)
- branch — tenant-scoped branches (RLS: tenant sees own branches)
- tenant_domain — domain mappings (RLS: tenant sees own domains)
- user — with tenantId column (RLS: tenant sees own users; superadmin sees all; user sees self)

Session variable approach:
- The Hono API sets `SET app.tenant_id = '<uuid>'` at the start of each request
- RLS policies read `current_setting('app.tenant_id', true)` and use it for filtering
- Superadmin sets a special value (or leaves unset) to bypass RLS

Better Auth tables (session, account, verification) do NOT need RLS — they are never queried by tenant scope directly. Session belongs to a user who belongs to a tenant — the user-level RLS on the user table prevents tenant leakage through joins.
</interfaces>

    1. **Create `apps/api/src/db/rls.ts`** — RLS helper:
       ```typescript
       /** @format */
       
       import { sql } from 'drizzle-orm';
       import { db } from './index';
       
       /**
        * Set the app.tenant_id PostgreSQL session variable for RLS policies.
        * 
        * Must be called at the start of each request to ensure RLS policies
        * use the correct tenant context.
        * 
        * @param tenantId - The tenant ID to scope the session to, or null for superadmin
        */
       export async function setRLSTenantContext(tenantId: string | null): Promise<void> {
         if (tenantId) {
           await db.execute(
             sql`SELECT set_config('app.tenant_id', ${tenantId}, true)`,
           );
         } else {
           // Set a special value for superadmin/unauthenticated
           // RLS policies will check for this value
           await db.execute(
             sql`SELECT set_config('app.tenant_id', 'superadmin', true)`,
           );
         }
       }
       
       /**
        * Get the current tenant_id from PostgreSQL session.
        * Returns null if not set (e.g., superadmin with no override).
        */
       export async function getRLSTenantContext(): Promise<string | null> {
         const result = await db.execute(
           sql`SELECT current_setting('app.tenant_id', true) AS tenant_id`,
         );
         const value = result.rows[0]?.tenant_id;
         if (!value || value === 'superadmin') {
           return null;
         }
         return value as string;
       }
       ```

    2. **Create `apps/api/src/db/migrations/0003_add_rls.sql`** — RLS migration:
       ```sql
       -- RLS: Defense-in-depth for tenant isolation
       -- Every tenant-scoped table gets RLS enabled with policies
       -- that use app.tenant_id session variable set by the application.
       
       -- ── Helper function: check if user can access a tenant's data ──
       CREATE OR REPLACE FUNCTION is_tenant_accessible(check_tenant_id uuid)
       RETURNS boolean AS $$
       DECLARE
         session_tenant text;
       BEGIN
         session_tenant := current_setting('app.tenant_id', true);
         
         -- Superadmin (no tenant scope) can see all
         IF session_tenant IS NULL OR session_tenant = 'superadmin' THEN
           RETURN true;
         END IF;
         
         -- Check if the requested tenant matches the session tenant
         RETURN session_tenant = check_tenant_id::text;
       END;
       $$ LANGUAGE plpgsql STABLE;
       
       -- ── Tenant table ──
       ALTER TABLE "tenant" ENABLE ROW LEVEL SECURITY;
       
       CREATE POLICY tenant_isolation ON "tenant"
         FOR ALL
         USING (is_tenant_accessible(id));
       
       -- ── Branch table ──
       ALTER TABLE "branch" ENABLE ROW LEVEL SECURITY;
       
       CREATE POLICY branch_isolation ON "branch"
         FOR ALL
         USING (is_tenant_accessible(tenant_id));
       
       -- ── Tenant domain table ──
       ALTER TABLE "tenant_domain" ENABLE ROW LEVEL SECURITY;
       
       CREATE POLICY tenant_domain_isolation ON "tenant_domain"
         FOR ALL
         USING (is_tenant_accessible(tenant_id));
       
       -- ── User table ──
       ALTER TABLE "user" ENABLE ROW LEVEL SECURITY;
       
       -- Users can always see their own record
       CREATE POLICY user_self_access ON "user"
         FOR ALL
         USING (
           id = current_setting('app.tenant_id', true) -- This is intentionally wrong!
         );
       
       -- Actually, user RLS needs a different approach since we can't compare
       -- the user's ID from a session variable easily. Let's use a simpler model:
       
       -- Drop and recreate the user policy properly:
       DROP POLICY IF EXISTS user_self_access ON "user";
       
       -- Users can see their own record OR users in their tenant
       CREATE POLICY user_isolation ON "user"
         FOR ALL
         USING (
           -- Superadmin bypass
           current_setting('app.tenant_id', true) IS NULL
           OR current_setting('app.tenant_id', true) = 'superadmin'
           -- Or same tenant
           OR tenant_id::text = current_setting('app.tenant_id', true)
         );
       
       -- ── Note on Better Auth tables ──
       -- session, account, verification tables are NOT tenant-scoped directly.
       -- They relate to users who are tenant-scoped. RLS on the user table
       -- prevents tenant leakage through user-level joins.
       -- These tables do not have tenantId columns and are excluded from RLS.
       ```

       **Wait — correct the user RLS policy.** The `current_setting('app.tenant_id', true)` returns the tenant UUID (as text), not the user ID. The user RLS policy should compare the user's `tenant_id` column with the session's tenant ID. Let me fix the migration:

       ```sql
       -- Corrected user RLS policy:
       CREATE POLICY user_isolation ON "user"
         FOR ALL
         USING (
           -- Superadmin bypass
           current_setting('app.tenant_id', true) IS NULL
           OR current_setting('app.tenant_id', true) = 'superadmin'
           -- Or same tenant (cast both to text for comparison)
           OR tenant_id::text = current_setting('app.tenant_id', true)
         );
       ```

## Threat Model

### Trust Boundaries
| Boundary | Description |
|----------|-------------|
| `Hono API → PostgreSQL` | RLS policies enforce tenant isolation at database level |
| `PostgreSQL session variable` | app.tenant_id is session-scoped, isolated from other connections |

### STRIDE Threat Register
| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-27 | Elevation of Privilege | RLS bypass | mitigate | RLS policies use `using` clause that checks `current_setting`. This is server-enforced, non-bypassable by the application. Even direct SQL injection would need to set the session variable correctly. |
| T-02-28 | Information Disclosure | RLS error message | mitigate | The `current_setting(..., true)` second parameter prevents errors when the setting is unset. Returns null instead of throwing. |
| T-02-29 | Elevation of Privilege | Superadmin RLS bypass | accept | Superadmin bypass is intentional design. RLS allows 'superadmin' value to see all rows. The superadmin role is protected by Better Auth authentication and cannot be self-assigned. |
| T-02-30 | Spoofing | Session variable leakage | mitigate | PostgreSQL session variables are isolated per-connection. The connection pool (`max: 10`) means a reused connection could have a stale tenant_id. Fix: Always set app.tenant_id before any query in the request lifecycle. The tenant middleware sets it before `await next()`, ensuring all downstream queries use the correct context. |
