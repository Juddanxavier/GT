## Objective

Add an inline "Assigned To" section on the shipment detail page that shows the current customer and allows changing them.

## Tasks

### 3.1 Add assigned-customer data to detail endpoint

- Current `GET /api/shipments/:id` returns `customerId` (which is really `userId`). Ensure it also returns `userId` in the response.
- Add a join to `user` table to resolve `customerName` directly from the user record instead of relying on `shipment.customerName` (which can become stale after profile updates).

### 3.2 Build AssignedTo section component

- New component: `apps/admin/components/assigned-to.tsx`.
- Sections:
  - **Current assignee card**: Shows user name, email, phone. If unassigned: "Unassigned — claimable via portal".
  - **Change button**: Opens an inline selector (modal or dropdown).
  - **Selector**: Reuse the same autocomplete component from Plan 2 (or a simpler version) to pick a new customer.
  - **Unassign button**: Option to remove assignment (set `userId` to null) — with confirmation dialog.
- States: Loading skeleton, error state, empty (unassigned).

### 3.3 Integrate into shipment detail page

- Add `apps/admin/app/(dashboard)/shipments/[id]/page.tsx`:
  - Place `AssignedTo` section prominently (above or alongside current details).
  - Use cached customers list for the autocomplete (or fetch via search endpoint).
- Wire the PATCH `/api/shipments/:id/assign` mutation.

### 3.4 Add reassign mutation hook

- `apps/admin/lib/queries.ts`: Add `useAssignShipment()` mutation.
- On success: invalidate `['shipments']`, show toast with customer name.
- On error: show error toast.

### 3.5 Reassign notification in UI

- When reassign succeeds, show toast: "Assigned to {customerName}. A notification has been sent."
- If notification fails (logged server-side), toast still shows success — notification failure is non-blocking.
