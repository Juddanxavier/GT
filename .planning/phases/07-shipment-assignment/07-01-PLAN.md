## Objective

Fix the `customerId: null` Zod validation bug (production 400 error) and create the reassign endpoint that admin needs to change which customer owns a shipment.

## Tasks

### 1.1 Fix Zod `customerId: null` validation

- Root cause: `createShipmentSchema` uses `uuidSchema.optional().nullable()`. In Zod 4, `.nullable()` on a schema with `.transform()` (`stripHtml`) can silently reject `null` depending on the field's position in the object. The `customerId` field is chained as `z.string().uuid().transform(stripHtml).optional().nullable()` — `null` reaches the `.string()` before `.nullable()` catches it.
- Fix: Restructure to `z.string().uuid().transform(stripHtml).nullable().optional()` or as a union `z.null().or(uuidSchema.optional())`.
- Add test coverage: `validators/index.test.ts` — test `createShipmentSchema` with `customerId: null` explicitly.

### 1.2 Add `PATCH /api/shipments/:id/assign` endpoint

- New route in `apps/api/src/routes/shipments.ts`.
- Authorization: `requireRole('superadmin', 'tenant-admin')`.
- Input: `{ userId: string | null }` — `null` to unassign, UUID to link.
- Validate `userId` belongs to same tenant and has role `'customer'`.
- Handle cases:
  - Assigning a different customer (reassign): update `shipment.userId`, set `customerName` from user's name, clear `contactEmail`/`contactPhone` (will use profile values), trigger notification to new customer.
  - Unassigning (set to null): keep `contactEmail`/`contactPhone` as-is so the shipment remains reachable.
  - Reassigning to same customer: no-op.
- Invalidate caches: `shipments:${id}`, `shipments:list:*`, `dashboard:*`.
- Log audit: event `SHIPMENT_REASSIGNED` with old/new userId.

### 1.3 Notify new customer on reassign

- After successful reassign, enqueue a notification via `notificationQueue.add('notify', ...)` with a new `SHIPMENT_ASSIGNED` event type or similar.
- Use the new customer's `email`/`phone` from the `user` table.
- If no contact info on new customer, skip notification (logged).

### 1.4 Refine create handler for unassigned shipments

- The create handler currently requires `customerId` to either be a valid UUID or `null`/`undefined`. Confirm the null path works: when `customerId` is null, `userId` in DB insert should be `null` (unassigned).
- The "Self" option (`customerId === 'self'`) sets `userId` to the creating user's ID. Keep this behavior.
- Remove the `auto-match` block (lines 229-247 in shipments.ts) that looks up user by contact email/phone after creation — this is race-prone and adds confusion. Unassigned stays unassigned until explicitly linked.

### 1.5 Update response validation schemas

- `apps/admin/lib/validation.ts`: `customerId` → `z.string().nullable()` (matches API wire format).
- Add `userId` field to response schemas where missing (admin needs it for reassign UI).
